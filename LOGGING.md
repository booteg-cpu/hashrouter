# Диагностика Hash Router 82.0.22

INFO: запуск/остановка, конфигурации, каталог алгоритмов, подключение/авторизация входов и выходов, первые задания, отключения, ошибки, повторные подключения, истечение источника и сводки выходов каждые 30 секунд.

DEBUG дополнительно записывает задания, сложность, переключения выходов и результат каждой шары со временем ответа. Включайте для замеров: он увеличивает объём журнала. Сырые Stratum-сообщения, заголовки HTTP, ключи, пароли и текст исключений не записываются. Известные реквизиты дополнительно исключаются из текстовых полей.

В SBP 82.0.19: **Hash Router → Логи роутера → VPS**. Фильтры алгоритма/уровня, автообновление 3 секунды, переключение DEBUG на сервере, сохранение полученных строк JSONL. Переключение уровня временное: после рестарта действует `log_level` из `/etc/hash-router/config.json` (по умолчанию INFO). Маршрутизация не меняется.

`router-events.jsonl` хранится рядом с файлом состояния (обычно `/var/lib/hash-router`). Ротация: текущий файл до 5 MiB и три предыдущих. API отдаёт последние 2000 событий, по 1–500 за запрос. Окно SBP хранит до 5000 полученных строк; сохранение экспортирует их, а не полный архив VPS. Пропуски отмечаются явно.

Служба пишет на диск в отдельном потоке с очередью 4096 событий. Заполненная очередь пропускает запись на диск, не задерживая Stratum; счётчик виден в API/SBP. При ошибке диска доступен буфер памяти. Авария процесса может потерять ещё не записанный хвост. Сохранённый хвост восстанавливается после рестарта; обновление не удаляет архивы.

API использует прежние HTTPS, токен и проверку сертификата:

- `GET /v2/logs?after=0&limit=300&level=DEBUG&algorithm=scrypt&stream=...` — записи, курсор `next`, идентификатор `stream`, флаги `gap`/`reset`, состояние записи на диск. Пустой algorithm выбирает все алгоритмы. Следующий запрос передаёт возвращённые next и stream; курсор учитывает строки, исключённые фильтром.
- `PUT /v2/logging` с JSON `{"level":"DEBUG"}` или `{"level":"INFO"}` — временный уровень.

Оба endpoint требуют авторизации. MRR не используется. Успешные GET журналов/статуса не создают собственных событий.

Если служба не запустилась или HTTPS недоступен, журнал через SBP недоступен. Для диагностики запуска по SSH: `sudo journalctl -u hash-router -n 100 --no-pager`.

Проверки выпуска: 67 серверных тестов и 124 теста SBP прошли офлайн; живые MRR/VPS/ASIC не использовались.


В 82.0.22 события input_handshake_request и input_handshake_reply показывают известный метод, этап и status: ok/denied/error. ok подтверждает отправку ответа; не означает поддержку всех расширений configure или получение ответа клиентом. Отправляемые значения ответа не записываются. input_disconnected включает method, phase (await_request/handle_request/send_reply), subscribed, authorized, duration_ms и reason. connection_closed означает закрытый транспорт, без утверждения о причине на удалённой стороне. Если клиент молча отключается после subscribe, журнал покажет успешную отправку ответа subscribe и отсутствие authorize; причину решения клиента нужно проверять на стороне MRR/майнера. Предел 32 запросов/ответов на соединение ограничивает дополнительный журнал, обработка команд продолжается.

82.0.22: input_configure_result записывается после отправки ответа. extensions содержит только version-rolling, minimum-difficulty, subscribe-extranonce, info; status=unsupported означает false для запрошенных расширений. count — число неизвестных строк расширений; их имена и параметры не записываются. Событие ограничено первыми 32 запросами на соединение.

82.0.23: output_version_rolling показывает supported/unsupported и mask для SHA256 upstream. input_configure_result теперь показывает фактический результат и маску. Нет готовых совместимых выходов — unsupported; это не означает ошибку авторизации. Версия не гарантирует совместимость с конкретным MRR-клиентом до живой проверки.

82.0.24: input_work_sent — завершена отправка notify клиенту; input_submit_received — получена обрабатываемая шара; share_forward_attempt — начат запрос пулу; upstream_share_result — ответ accepted/rejected. Первые три события каждого этапа на соединение видны на INFO. input_flow_summary содержит накопленные счётчики каждые 30 с при опросе статуса и при отключении. Нулевой submits_received при положительном jobs_sent указывает на отсутствие обрабатываемых шар от входа, но не доказывает получение notify клиентом. Реквизиты и сырые сообщения не сохраняются.

82.0.25: jobs_sent считает фактическую отправку заданий, а не кванты планировщика. При неизменной работе счётчик и last_job_age_ms могут долго не обновляться — sender_running и работающий вход не обязаны выдавать notify каждую секунду.

82.0.26: input_submit_rejected.reason теперь различает submit_not_list, submit_parameter_count/type, job_unknown/wrong_connection/invalidated, extranonce2/ntime/nonce/version_bits_format, ntime_before_job, version_bits_outside_mask, output_session_stale, output_version_mask_changed/unsupported. INFO ограничен тремя событиями каждого типа на соединение; local_rejected остаётся общим счётчиком всех отказов. Структурные поля содержат только длины (hex-символы), ожидаемое число параметров, признаки job, его возраст и маску. invalidation_reason — clean_job, version_mask_changed, extranonce_changed или output_disconnected. Отсутствующий/нестроковый параметр имеет длину -1. Ошибка job_unknown может означать и удаление старого job по TTL/лимиту: это не доказывает, что job никогда не выдавался. Никакие значения worker/job ID/submit не записываются.
